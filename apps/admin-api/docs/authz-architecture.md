# admin-api 权限架构

## 目标

- 认证只确认当前请求的用户身份。
- 接口权限只确认当前用户能否执行指定操作。
- 菜单只负责展示页面入口和操作权限，不承担数据范围控制。
- 角色与菜单通过 `sys_role_menu` 显式关联。

## 认证

- `AuthService` 负责登录、刷新令牌和读取当前用户。
- `AuthGuard` 负责校验 JWT，并把有效用户放入请求上下文。
- `@Public()` 标记无需认证的接口。
- `@AuthRequired()` 标记需要认证但不要求具体操作权限的接口。
- 认证失败统一返回未认证错误。

## 接口权限

- `@RequirePermissions()` 声明接口需要的操作编码。
- `PermissionGuard` 读取声明的操作编码并调用 `PermissionService` 校验。
- `PermissionService` 只认启用、未删除的角色、菜单和角色菜单关系。
- 超级管理员由特殊角色编码识别，拥有全部操作权限。
- 普通用户必须拥有接口声明的全部操作编码。
- 接口权限不负责过滤业务数据；业务 Service 按业务条件查询数据。

## 菜单类型

- `page`：页面入口，必须有页面路径和组件。
- `menu`：菜单层级节点，用来组织页面或子菜单。
- `external`：外部链接，必须有外链地址。
- `action`：操作权限，必须有唯一操作编码，不生成页面菜单。
- 菜单树只返回可访问、未删除且可显示的非操作节点。
- 操作编码只从 `action` 类型菜单中读取。

## 角色菜单关系

- `sys_role_menu` 是纯关联表，只保存角色 ID 和菜单 ID。
- 角色新增或更新菜单权限时，由角色 Service 显式校验并增量维护关系。
- 删除角色或菜单时，由所属业务 Service 显式清理关联记录。
- 不使用 ORM 集合方法、级联写入或隐式关系同步。
- 关系表不承担业务历史，历史审计由独立审计能力负责。

## 缓存

- `PermissionCacheService` 属于基础设施层，只负责权限和菜单缓存的读写与失效。
- Redis 不解析角色业务，也不计算授权规则。
- 用户、角色和菜单模块在数据变更后负责找出受影响用户并调用缓存失效方法。
- 缓存不可用时，权限查询必须回源数据库，不能放宽权限。
- 权限和菜单缓存按用户失效，缓存内容必须只来自有效数据。

## Service 边界

- Controller 只声明认证和接口权限，不拼装角色或菜单关系 SQL。
- Service 负责查询业务数据、校验业务状态和维护业务关联。
- 角色 Service 负责角色及角色菜单关系。
- 菜单 Service 负责菜单及其角色关联清理。
- 用户 Service 负责用户及用户角色、用户部门关系。
- 数据权限不是当前角色模型的一部分，不在角色、Guard、拦截器或 Redis 中维护。
