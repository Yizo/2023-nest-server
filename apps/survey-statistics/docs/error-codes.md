# 错误码约定

## 基本原则

大多数错误直接使用 HTTP 状态码：

| code | 含义 |
| --- | --- |
| 400 | 请求参数错误 |
| 401 | 用户名或密码错误等普通认证失败 |
| 403 | 已登录但没有权限 |
| 404 | 资源或接口不存在 |
| 409 | 数据冲突、重复提交 |
| 429 | 请求频率过高 |
| 500 | 未处理的服务端错误 |
| 503 | 数据库、Redis 或 migration 未就绪 |

只有前端必须执行不同动作的认证状态使用独立业务码。HTTP 状态仍保持 401，便于网关和监控正确识别。

| HTTP | 业务 code | 含义 | 前端动作 |
| --- | --- | --- | --- |
| 401 | 1001 | 缺少访问令牌 | 清理登录状态并跳转登录页 |
| 401 | 1002 | 访问令牌已过期 | 尝试刷新；失败后跳转登录页 |
| 401 | 1003 | 访问令牌无效 | 清理本地 Token 并跳转登录页 |
| 401 | 1004 | Refresh Token 无效或已过期 | 清理登录状态并重新登录 |
| 401 | 1005 | 用户不存在或已停用 | 清理登录状态并提示账号不可用 |

示例：

```json
{
  "code": 1002,
  "message": "登录已过期，请重新登录",
  "data": null,
  "requestId": "...",
  "timestamp": "..."
}
```

不要为每个模块、每个接口继续增加业务码。只有前端确实需要分支行为时，才评审新增全局业务码。
