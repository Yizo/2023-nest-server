# 架构决策与学习指南

这份文档解释当前实现为什么这样设计。它不是框架功能清单，重点是以后改需求时如何保持边界清晰。

## 为什么选择 MikroORM

| 维度 | TypeORM | Prisma | MikroORM |
| --- | --- | --- | --- |
| NestJS 使用体验 | 最普及，资料多 | Client 注入简单 | 官方 Nest 集成，实体与 DI 自然 |
| 数据建模 | 装饰器实体 | 独立 schema | TypeScript 实体 |
| 事务和聚合修改 | 能实现，但需要团队约束 | 事务 API 清晰 | Unit of Work 和 Identity Map 是默认模型 |
| 迁移 | 可用，必须禁用生产 synchronize | Prisma Migrate 体验好 | 显式迁移和实体模型配合紧密 |
| 复杂统计 SQL | Query Builder 或原生 SQL | 原生 SQL | 原生 SQL或业务专用 Query 类 |
| 本项目学习成本 | 低到中 | 低到中，但多一套 schema 语言 | 中等，概念集中且能学到事务边界 |

本项目选择 MikroORM，不是因为它在所有项目里都最好，而是它同时满足以下条件：

1. 数据库结构必须由显式迁移持续演进，应用启动不偷偷改表。
2. 用户、角色、问卷等写操作需要清晰的事务边界。
3. 简单 CRUD 直接使用 ORM，统计查询使用参数化 SQL，不再维护通用 Query Builder 封装。
4. 实体、DTO 和业务服务都使用 TypeScript，便于前端开发者逐层理解。

生产环境禁止使用自动同步表结构。`MikroORM` 配置只注册实体和迁移器，迁移由部署工具单独执行。

## 模块边界

```text
HTTP / WebSocket
        ↓
Controller：校验输入、声明权限
        ↓
Service：业务规则、事务、写入
        ↓
MikroORM EntityManager / 业务专用 Query
        ↓
PostgreSQL

事务提交后
        ↓
BullMQ：通知、错误聚合、清理、巡检、补偿
        ↓
Redis Pub/Sub：在线用户实时事件
```

- Controller 不拼 SQL，也不决定事务。
- Service 负责写模型和业务不变量。
- `*.queries.ts` 只处理列表、下一页标记和统计等读取逻辑。
- 原生 SQL 必须参数化；MikroORM `execute()` 统一使用 `?` 占位符。
- 队列不承担问卷提交等核心记录写入，Redis 暂时不可用不能让已提交答卷消失。

## 初始化不是应用启动钩子

系统生命周期中的初始化被拆成四类：

| 类型 | 例子 | 执行位置 | 是否可重复 |
| --- | --- | --- | --- |
| 结构和定义数据 | 表、索引、权限定义、必要配置 | 版本化 migration | 是，由迁移表保证只执行一次 |
| 首个秘密账号 | 平台所有者 | 显式 `bootstrap-admin` 工具 | 是，同邮箱重复执行不新增 |
| 动态业务数据 | 角色、菜单、字典项、业务配置 | 管理 API | 是，由业务约束保证 |
| 运行时调度 | 清理、补偿、完整性巡检 | `queue-schedule-sync` | 是，使用“存在则更新、不存在则创建” |

NestJS 正常启动只启动业务服务。它不会自动迁移、创建角色或覆盖配置；数据库版本不匹配时 readiness 返回 503。

## 角色为什么没有默认枚举

角色是数据库业务数据，不是代码常量。系统只内置稳定的权限码，管理员可以动态创建、禁用角色并调整权限。

如果未来某次版本确实要求增加一个产品内置角色，应在该版本的数据迁移中执行幂等的“存在则更新、不存在则创建”，并单独维护角色权限关系。不要重新加入 `super_admin/admin/user` 枚举，也不要在每次启动时反复写入。

`isPlatformOwner` 只解决“系统里还没有任何管理员时，谁来创建第一个角色”这个引导问题。它不是普通角色，也不参与后续角色迭代。

## 为什么消息队列保持小型

当前只有一个 `background` 队列和一个 Processor，任务通过不同 name 区分：

- 通知投递；
- 客户端错误聚合；
- 原始错误保留期清理；
- 待处理记录补偿；
- 无物理外键场景下的孤儿巡检。

任务载荷带版本号，实体任务使用合法且确定性的 job ID，失败有重试。数据库先记录 `pending` 状态；如果任务发布失败，每分钟 reconcile 会重新发现并补发，因此不需要在学习阶段引入 Kafka、RabbitMQ 或完整 Outbox 框架。

## 错误响应

业务不维护按模块划分的大量错误码：

- 成功：`code = 0`；
- 普通失败：`code = HTTP status`；
- 缺少 Token、Token 过期/无效等需要前端分支处理的认证状态使用 1001-1005；
- 参数细节放在 `data.errors`；
- 未知异常只向客户端返回通用 500 文案，完整堆栈进入服务端日志。

业务页面主要处理 400、401、403、404、409、429、500、503；认证基础设施额外处理少量全局业务码，详见 `error-codes.md`。
